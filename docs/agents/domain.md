# Domain Docs

本项目采用单一上下文的领域文档布局。

## 工作前读取

- `docs/context/PROJECT_CONTEXT.md`：项目目标、范围和当前待决策事项。
- 根目录 `CONTEXT.md`：已经确认的统一领域术语；文件尚不存在时静默继续。
- `docs/adr/`：与当前任务相关的架构决策；目录尚不存在时静默继续。

`CONTEXT.md` 和 `docs/adr/` 按需创建。只有当术语或重大决定真正达成共识后，才由 `domain-modeling` 或 `grill-with-docs` 写入，不提前填充待决策内容。

## CONTEXT.md

`CONTEXT.md` 只能是领域 glossary，不是需求文档、开发规范或方案草稿。

- 每个术语用一到两句话定义“它是什么”。
- 写清边界、归属、关系、业务标识和容易混淆的概念。
- 使用一个规范名称，把不推荐的同义词放入 `_Avoid_`。
- 不写表名、字段名、框架、流水线、迁移步骤和实现原因。

写入前检查：定义是否能经受存储或代码重构、产品人员是否需要理解、六个月后是否仍然成立。否则应写入 ADR、开发文档或项目上下文。

## ADR

只有同时满足以下条件才创建 ADR：

1. 决定难以逆转。
2. 缺少上下文时会让未来维护者困惑。
3. 存在真实替代方案和权衡。

若输出与已有 ADR 冲突，必须明确指出，不得静默覆盖。
